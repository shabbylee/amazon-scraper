# 抓取管道并发策略：串行执行，移除并发度配置

## 背景

`src/config.ts` 一直有 `MAX_CONCURRENT_ATTEMPTS`（默认 1，硬上限 2），`/api/health` 把它作为 `maxConcurrentAttempts` 上报，README 与 `.env.example` 把它描述成"并发 Attempt 上限"。

但抓取管道从未读过这个值：`runSearchJob` 是页内 `for` 循环 + 页间 `for` 循环的单线程串行结构，全仓库没有任何并发原语（信号量 / 任务池 / `Promise.all` 编排）。也就是说该项目对外宣称了一个不存在的能力：用户把它调到 2，行为不发生任何变化。这比缺少功能更糟——它让人以为提速是配置问题，而不是需要重新设计的问题。

另外 AGENTS.md 的抓取伦理里，"同一 Marketplace 相邻 Attempt 至少间隔 2 秒"与"并发 Attempt ≤ 2"这两条本身就互相冲突：一旦并发，就不存在"相邻 Attempt"这个可度量的时间关系。

## 决定

- **移除 `MAX_CONCURRENT_ATTEMPTS` 配置项**，`AppConfig` 不再有 `maxConcurrentAttempts` 字段，`/api/health` 不再上报该字段（breaking change）。
- **抓取管道保持串行**：同一 Job 内页与页、Attempt 与 Attempt 严格顺序执行，并发度恒为 1。
- **AGENTS.md 的硬约束收敛为**："相邻 Attempt ≥ 2 秒；管道串行执行，天然满足并发 ≤ 2 的上限"，不再暗示存在可调并发度。
- 该行为不需要配置项表达——它是一个结构性事实，不是运行时参数。

## 被拒绝的替代方案

- **实现并发控制（信号量，上限 2）**：与限速硬约束语义冲突。并发两个 Attempt 后，"相邻 Attempt 间隔 ≥ 2 秒"失去可度量的含义；要保留限速就必须引入跨 Attempt 的调度时钟，同时还要处理与"多代理每 Attempt 轮换（ADR-0003，每次重启浏览器）"的组合爆炸。这不是 bug 修复，是重新设计抓取调度，应单独开 ADR。
- **保留配置项并标注"暂未生效"**：把撒谎变成写在脸上的撒谎，仍然引导用户去调一个无效旋钮。
- **保留配置项但改为只影响前端提示**：让 README 的承诺继续存在而行为不变，问题原样保留。

## 后果

- `.env.example` 少一个变量，`/api/health` 少一个字段，README 配置表与响应示例同步删除——属于破坏性变更，需在提交信息标注 `!`。
- 串行实现天然满足 AGENTS.md 的并发上限，抓取伦理没有任何放松。
- 若将来确实需要提速，正确的方向是重新定义限速语义（例如"同一 Marketplace 每分钟最多 N 次导航"）并单独开 ADR，而不是恢复这个字段。
